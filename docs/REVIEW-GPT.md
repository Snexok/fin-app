# Код-ревью backend (GPT/Codex)

Статическое ревью приведённого кода относительно требований из сообщения. Полный ARCHITECTURE.md и тесты не предоставлены; заявленные 87 тестов не проверены. Файлы не изменялись.

- **High · `app/api/v1/finance/simulations/route.ts:20`, `lib/engine/dates.ts:57,69` · Бесконечный цикл через публичный API.**  
  `Number.isInteger(0)` возвращает `true`, поэтому `recurring.everyN=0` достигает генераторов. Месячный цикл не увеличивает `i`, недельный не изменяет дату. Запрос блокирует event loop; тайм-аут HTTP не остановит синхронный цикл.  
  **Исправление:** проверять `everyN` на целое положительное число с верхней границей на уровне API и внутри обоих генераторов. Ограничить число генерируемых событий и длину горизонта. Неверное значение возвращает 422.

- **High · `lib/auth.ts:142–155`, `lib/finance-service.ts:150–153` · Привязка может удалить параллельно созданный бюджет.**  
  `confirmLink` проверяет наличие `books` без блокировки общего объекта аккаунта. Между `hasBook()` и `DELETE FROM users` другой запрос может сохранить план. Удаление пользователя каскадно удалит уже созданные бюджет, операции и события. Блокировка Telegram identity не защищает `savePlan`.  
  **Исправление:** ввести общий протокол блокировок для привязки и финансовых команд: блокировать строки обоих `users` в стабильном порядке, затем проверять бюджеты и переносить identity. После ожидания блокировки повторно проверять владельцев и условия слияния. Удаление исходного аккаунта выполнять только после проверки отсутствия финансовых данных под этими блокировками.

- **High · `lib/inbox.ts:7–15`, `app/api/telegram/route.ts:23–32` · Inbox допускает потерю апдейтов и повторное выполнение побочных эффектов.**  
  Захват коммитится до обработки. Если процесс завершится после захвата, `processed_at` останется `NULL`, а все повторы навсегда получат 200. Параллельный повтор также получает 200, пока первая обработка ещё может завершиться ошибкой. Обратная проблема: после частичного выполнения удаление inbox позволяет повторно создать proposal, decision или продвинуть онбординг.  
  **Исправление:** атомарно сохранять update и задание, возвращать 200 после сохранения, обрабатывать worker с lease/retry. Изменения состояния привязывать к уникальному `(botId, update_id, action)`, отправку сообщений проводить через outbox. Простое удаление отметки не обеспечивает безопасный retry.

- **High · `app/api/telegram/route.ts:25–32`, `lib/bot.ts:119–124` · Тайм-аут webhook может запустить вторую обработку одновременно с первой.**  
  `webhookCallback` использует стандартный тайм-аут 10 секунд. Здесь STT может занимать 30 секунд, скачивание ещё 20 секунд, два LLM-вызова до 16 секунд. Истечение webhook-тайм-аута не отменяет уже выполняющуюся бизнес-логику; обработчик удаляет inbox-захват, разрешая повтор. [Документация grammY](https://grammy.dev/guide/deployment-types).  
  **Исправление:** вынести долгую обработку из webhook в durable job. До этого нельзя освобождать захват, пока исходная обработка ещё способна изменять состояние; увеличение тайм-аута само по себе проблему не решает.

- **High · `lib/finance-service.ts:33–47,99–105,234–245` · Прогноз собирается из разных версий бюджета.**  
  Чтение `books`, операций, обязательств и цели выполняется отдельными запросами без согласованного snapshot. Например, баланс прочитан до подтверждения оплаты аренды, а оставшаяся сумма аренды после него. В результате прогноз одновременно не списывает фактический расход и уже убирает обязательство. `financeVersion` относится к первой выборке, хотя расчёт использует более новые данные. В PostgreSQL даже обычная транзакция `READ COMMITTED` не исправит это. [Документация PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).  
  **Исправление:** загружать весь расчёт в одной транзакции `REPEATABLE READ`, одним SQL snapshot либо под общей блокировкой бюджета. В `simulate` сохранять decision с версией именно того snapshot, по которому рассчитан результат.

- **High · `lib/finance-service.ts:34–38,152–155` · Граница нового остатка теряет микросекунды через `pg`.**  
  `opening_as_of` читается как JavaScript `Date` и передаётся обратно в SQL. `pg` обрезает микросекунды до миллисекунд. Например, операция создана в `.123100`, новая точка отсчёта в `.123900`; после преобразования граница становится `.123000`, и старая операция повторно попадает в баланс. [Документация node-postgres](https://node-postgres.com/features/types).  
  **Исправление:** сравнивать timestamps непосредственно в SQL, например через JOIN с `books`, без передачи границы через JS. Надёжнее использовать явную ревизию точки отсчёта и принадлежность операций этой ревизии.

- **High · `lib/engine/forecast.ts:71–76`, `lib/engine/purchase.ts:40–46` · Просроченная цель освобождает все ещё не накопленные деньги.**  
  Для цели с прошедшим сроком устанавливается `goalOverdue`, но `N` остаётся нулём, поэтому `Q(k)=0`. Вчерашняя недофинансированная цель сегодня перестаёт уменьшать свободные деньги. Более того, `deadlineFeasible` может стать `true` для уже пропущенного срока.  
  **Исправление:** явно определить политику просроченной цели. До уточнения срока сохранять требуемое финансирование `L` как текущую защищённую потребность либо возвращать неопределённую оценку. Для пропущенного срока при `L>0` нельзя возвращать `deadlineFeasible: true`.

- **High · `lib/coach.ts:104–109` · Проверка Evidence позволяет превратить отрицательную сумму в положительную.**  
  Для текста `потратил -500` модель может вернуть `priceText: "500"`. Проверка `includes` проходит, парсер фрагмента возвращает положительную сумму, а `regex.error === "NEGATIVE_AMOUNT"` теряется при сборке результата. Создаётся предложение расхода на 500. Аналогично допускаются подстроки внутри других чисел.  
  **Исправление:** принимать только полный денежный токен с исходными границами, знаком и единицей измерения. Использовать позиции кандидатов из исходного текста. Ошибки детерминированного парсера нельзя стирать результатом LLM.

- **High · `lib/engine/purchase.ts:29–35`, `lib/coach.ts:36,64` · Неизвестные необходимые расходы допускают безусловное «Можно».**  
  При `essentialDailyMinor=null` движок фактически проверяет нулевые повседневные расходы и может вернуть `fits_plan`. Текст начинает ответ с разрешающего вердикта; поздняя фраза про еду и транспорт не показывает, что возможность покупки не установлена. Это осознанное отклонение в BACKEND.md, но оно меняет смысл оценки платёжеспособности.  
  **Исправление:** возвращать `insufficient_data` либо отдельную явно условную оценку без вердикта `yes`. Показывать рассчитанную верхнюю границу до неизвестных расходов и запрашивать необходимый минимум.

- **High · `lib/session.ts:24–29`, `lib/coach.ts:119–141`, `app/api/stt/route.ts:9–17` · Платные операции доступны без ограничений потребления.**  
  Анонимную сессию можно бесплатно получить через GET, затем неограниченно вызывать STT. Создав план, можно неограниченно вызывать LLM. Наличие сессии здесь не ограничивает злоупотребление, поскольку аккаунты создаются самим атакующим.  
  **Исправление:** до вызовов провайдеров применять распределённые лимиты по пользователю и IP, лимит одновременных запросов и общий бюджет потребления. Ограничивать создание анонимных аккаунтов и длительность аудио.

- **Medium · `lib/coach.ts:162–164`, `lib/parse.ts:91–95`, `lib/proposals.ts:170` · Исторические даты операций искажаются.**  
  При сегодняшней дате 15 октября фраза `потратил 500 14.10` разбирается как 14 октября следующего года, после чего молча заменяется сегодняшним днём. Явная будущая дата также молча заменяется сегодня. Для действительно принятой прошлой даты записывается полдень UTC: в `Pacific/Kiritimati` это уже следующий календарный день.  
  **Исправление:** разделить разбор дат плановых и фактических событий. Будущую дату факта отклонять или уточнять. Хранить дату операции отдельным `date` либо преобразовывать её в timestamp с учётом зоны пользователя, сохраняя исходную локальную дату.

- **Medium · `lib/auth.ts:10–12,22,56`, `lib/coach.ts:207` · Часовой пояс пользователя фактически недоступен для настройки.**  
  Все доступные пути создания аккаунта используют Москву; API изменения зоны отсутствует. Онбординг дополнительно вычисляет дату из `opts.timezone`, которую бот не передаёт, вместо чтения `users.timezone`. Даже при изменённой в БД зоне онбординг и прогноз могут понимать «сегодня» по-разному.  
  **Исправление:** добавить валидируемый контракт выбора IANA timezone и читать сохранённую зону в онбординге. Использовать один источник зоны во всех пользовательских сценариях.

- **Medium · `lib/coach.ts:157–159` · Любое поступление автоматически погашает единственный ожидаемый доход.**  
  Если просрочена одна зарплата, сообщение `пришёл кэшбэк 1000` без совпадения по названию привяжется к ней и уменьшит её остаток. Это другая экономическая операция: кэшбэк не является частичным поступлением зарплаты.  
  **Исправление:** автоматическую привязку разрешать только при однозначном совпадении смысла и названия. При отсутствии совпадения создавать отдельное поступление или отдельно спрашивать, закрывает ли оно ожидаемый доход.

- **Medium · `lib/finance-service.ts:216–222` · Совместимый профиль восстанавливает уже погашенный доход.**  
  Когда доход полностью погашен, он отсутствует в `nextIncome` и `overdueIncomes`, но fallback возвращает его исходную сумму через `lastIncome.amountMinor`. Повторное сохранение полученного профиля создаёт новое обязательство дохода на уже полученную сумму.  
  **Исправление:** не возвращать погашенный occurrence как предстоящий доход. Для старого контракта использовать нулевую сумму либо явный признак отсутствия следующего дохода; обеспечить безопасный цикл GET → редактирование → POST.

- **Medium · `lib/proposals.ts:156–160,164–166` · Новая ревизия устаревшего предложения не пересчитывает его смысл.**  
  Меняются только `revision` и `base_finance_version`. Сумма, связь с обязательством и допущение `alreadyIncludedInBalance` остаются прежними. Если за это время обязательство частично или полностью погасили, повторное подтверждение старой суммы всё равно принимается. После сброса плана предложение получает новую ревизию, хотя связанный occurrence уже отменён.  
  **Исправление:** при stale повторно валидировать payload относительно текущего бюджета. Зависимые суммы пересчитывать с явным показом изменений; недействительные связи требовать выбрать заново. Только после этого выдавать подтверждаемую ревизию.

- **Medium · `lib/coach.ts:124–125,161`, `lib/ai/llm.ts:17` · Уточняющие вопросы часто не имеют рабочего продолжения.**  
  После `Сколько потратили?` или `Сколько пришло?` состояние ожидающей операции не сохраняется: ответ `500` не создаёт предложение. Для покупки состояние есть, но при включённой LLM схема не допускает `amount_only`, а `intentFromLlm` заменяет корректное regex-намерение намерением модели.  
  **Исправление:** хранить тип ожидаемого действия, описание и привязку к occurrence. Обрабатывать ответ суммой до вызова LLM; добавить отмену и срок жизни черновика. Покрыть все три уточняющих сценария.

- **Medium · `lib/parse.ts:18,64–71`, `lib/coach.ts:129–164` · Парсер теряет денежные суммы и игнорирует неоднозначность.**  
  `stripDates` удаляет `15.50` как потенциальную дату, хотя это допустимая денежная запись. Для нескольких кандидатов выставляется `ambiguous`, но чат и онбординг всё равно выбирают последнюю сумму. Детерминированный выбор не делает исходный запрос однозначным.  
  **Исправление:** различать даты и суммы по контексту, единицам и валидности календарной даты. При нескольких правдоподобных суммах возвращать уточнение, а не готовить финансовое действие.

- **Medium · `lib/finance-service.ts:179–203`, `lib/engine/money.ts:16` · Денежные границы используют разные правила округления и неполную валидацию.**  
  `toMinor` использует `Math.round(v*100)`, `rublesToMinor` использует `toFixed(2)`: для `2.675` получаются 268 и 267 копеек. `balanceMinor` не проверяется по диапазону, отрицательный доход молча удаляется фильтром `amountMinor > 0`.  
  **Исправление:** использовать единый строгий денежный парсер. Строки рублей разбирать десятично, лишние знаки после запятой отклонять либо применять одно документированное правило. Для баланса проверять допустимый знаковый диапазон; отрицательный доход отклонять до фильтрации.

- **Medium · `lib/engine/forecast.ts:128`, `lib/engine/legacy.ts:115`, `lib/engine/purchase.ts:65` · Дата разрыва не соответствует показанной сумме.**  
  `Gap` соединяет первую дату отрицательного значения с максимальным дефицитом за весь горизонт. Например, 16 октября не хватает 100 ₽, 20 октября 10 000 ₽; ответ утверждает, что 16 октября не хватит 10 000 ₽. Дополнительно `mandatory ?? essential` выбирает тип сигнала, а не самый ранний разрыв.  
  **Исправление:** хранить отдельно первую дату и дефицит в этой точке, максимальный дефицит и его дату. Для общего предупреждения выбирать самый ранний сигнал, сохраняя его тип.

- **Medium · `lib/engine/purchase.ts:40–46`, `lib/coach.ts:63` · Недостаток резерва выдаётся за доказанный сдвиг цели.**  
  В `goalImpact.protectedShortfallMinor` попадает общий дефицит `R+S+Q`. Он может возникнуть исключительно из-за резерва, в том числе при полностью накопленной цели. Бот всё равно утверждает: `План накоплений на цель сдвинется`, хотя движок возвращает неизвестный срок.  
  **Исправление:** разделить дефицит резерва и финансирования цели либо честно показывать общий защищённый дефицит без атрибуции. Не утверждать сдвиг срока, пока он не установлен расчётом.

- **Medium · `lib/auth.ts:54–57`, `lib/finance-service.ts:150–153` · Блокировки отсутствующей строки не сериализуют создание.**  
  Два первых апдейта одного Telegram-пользователя могут одновременно не найти identity и попытаться вставить одинаковый subject. Аналогично два первых сохранения плана проходят пустой `SELECT ... FOR UPDATE`, затем конфликтуют по `books.user_id`. Один обычный запрос получит необработанную ошибку уникальности.  
  **Исправление:** сериализовать создание по существующей строке пользователя или advisory lock по стабильному ключу. Для Telegram identity использовать безопасный UPSERT с получением победившего владельца и откатом лишнего создания пользователя.

- **Medium · `lib/conversation.ts:6–18`, `lib/coach.ts:208–256` · Состояние онбординга обновляется с потерей параллельных сообщений.**  
  Два разных update читают одинаковый `step`, независимо интерпретируют ответы и перезаписывают состояние. Inbox защищает только от одинакового `update_id`. В результате сообщения могут попасть не в те поля или одно из них исчезнет.  
  **Исправление:** обрабатывать сообщения последовательно для `(userId, channel)` и использовать транзакционный переход состояния с ревизией/CAS. Завершение онбординга и сохранение плана должны иметь устойчивый идентификатор команды.

- **Medium · `lib/db.ts:59,93–101` · Ошибка миграции может оставить соединение пула в открытой аварийной транзакции.**  
  `BEGIN ... COMMIT` отправляется через `pool.query`. При ошибке до COMMIT клиент освобождается с незавершённой транзакцией, а отдельный `db.exec("ROLLBACK")` может получить другое соединение. Параллельные migrator также читают один список `done` и выполняют одну миграцию одновременно.  
  **Исправление:** выполнять миграции на выделенном клиенте с гарантированным rollback на нём же. Брать PostgreSQL advisory lock до чтения списка применённых миграций. [Требование одного клиента для транзакции](https://node-postgres.com/features/transactions).

- **Medium · `lib/api.ts:32–36` · Проверка Origin не проверяет полный origin и доверяет forwarding-заголовку.**  
  Сравнивается только `host`, без протокола; запросы без обоих защитных заголовков принимаются. `x-forwarded-host` считается доверенным независимо от конфигурации proxy. Это неполная защита для клиентов без Fetch Metadata и установок, где proxy не очищает входящий заголовок.  
  **Исправление:** сравнивать полный origin с настроенным каноническим URL приложения. Доверять forwarded-заголовкам только от контролируемого proxy. Для cookie-auth mutations без проверяемого Origin требовать CSRF-токен или явно отклонять запрос.

- **Medium · `lib/api.ts:40–41`, `app/api/stt/route.ts:10–15` · Ограничения размера срабатывают после загрузки тела в память.**  
  `req.text()` и `req.formData()` сначала читают весь запрос. `Content-Length` необязателен и не является надёжным ограничителем, а `text.length` считает UTF-16 символы вместо байтов. Большой chunked-запрос может исчерпать память до проверки.  
  **Исправление:** ограничивать тело на ingress и при потоковом чтении по фактическому числу байтов. Для multipart ограничивать суммарный размер, число частей и размер каждого файла до полного разбора.

- **Medium · `lib/bot.ts:102–104` · Отмена уже применённого предложения сообщает ложный результат.**  
  `rejectProposal` возвращает applied-предложение без отмены записи, но бот отвечает `ничего не записал`. Это возможно при гонке двух кнопок или устаревшей клавиатуре. Пользователь считает расход отменённым, хотя он остаётся в балансе.  
  **Исправление:** проверять возвращённый статус. Для `applied` сообщать, что запись уже сохранена; отмена должна быть отдельным подтверждаемым сторно. Для expired/rejected также использовать соответствующий текст.

- **Medium · `lib/finance-service.ts:241–244`, `db/migrations/001_core.sql:10` · История запросов сохраняется при выключенном `history_enabled`.**  
  По умолчанию флаг равен `false`, однако `simulate` всегда сохраняет исходный вопрос, а `/api/profile` всегда возвращает историю. Пользовательские финансовые формулировки сохраняются независимо от заявленного состояния настройки.  
  **Исправление:** проверять настройку перед сохранением текста вопроса и пользовательской истории. Если технический аудит расчёта обязателен, хранить минимальный структурированный расчёт отдельно от истории диалога, с заданным сроком хранения.

- **Medium · `lib/ai/llm.ts:49–51` · Отсутствие цифр не делает LLM-вступление безопасным.**  
  Фразы `Смело покупайте` или `Денег точно хватит` проходят фильтр и показываются перед отрицательным расчётом. Это позволяет недоверенному тексту модели подменять смысл детерминированного вердикта.  
  **Исправление:** использовать фиксированные вступления по `assessment` либо убрать свободный генеративный текст из ответа с финансовым решением.

- **Low · `app/api/v1/chat/messages/route.ts:3`, `lib/proposals.ts:146`, `app/api/v1/proposals/[id]/confirm/route.ts:15` · Контракт ошибок v1 неоднороден.**

  **Исправление:** нормализовать все v1-ошибки одним сериализатором; старую форму сохранять только на legacy-маршруте.

- **Low · `lib/proposals.ts:122`, `app/api/v1/proposals/[id]/confirm/route.ts:14–15` · Идемпотентность HTTP-ответа слабее задокументированной.**  
  Отсутствующий ключ молча заменяется серверным, длинный ключ обрезается, а повтор получает новый прогноз, добавленный после чтения сохранённого результата. Тот же ключ может вернуть финансовое состояние другой версии.  
  **Исправление:** валидировать обязательность и длину `Idempotency-Key`, не обрезать его. Сохранять согласованный ответ команды целиком либо явно разделить неизменяемый результат команды и отдельно запрашиваемое текущее состояние.

- **Low · `db/migrations/001_core.sql:128–133`, `lib/finance-service.ts:38–46` · Индексы не соответствуют основным агрегатам.**  
  Остаток выбирается по `created_at`, но индекс построен по `occurred_at`. Погашения считаются коррелированным подзапросом по `occurrence_id`, для которого нет подходящего индекса. С ростом истории каждый прогноз повторно сканирует значительную часть операций.  
  **Исправление:** добавить индексы `(user_id, created_at)` и `(user_id, occurrence_id)` с нужными включёнными полями; погашения агрегировать один раз и присоединять к occurrences.

- **Low · `app/api/health/route.ts:10–14` · Health раскрывает конфигурацию интеграций вопреки документации.**  
  Публичный ответ сообщает тип БД, наличие LLM, bot token и webhook secret. Для readiness эти сведения не нужны.  
  **Исправление:** возвращать только доступность сервиса; диагностические признаки оставить в закрытом endpoint или логах.
