# Стоимость LLM на DAU

Критерий приёмки 5: оценка стоимости LLM на одного активного пользователя в день (DAU) на основе предположений об использовании в Core Product Loop.

Разделы 2–6 — оценка по предположениям. С миграции 009 фактический расход измеряется: каждая попытка вызова модели пишется в журнал `ai_usage` с токенами из ответа провайдера и стоимостью по таблице цен ниже. Как считать реальную стоимость на DAU — [§7](#7-как-измеряется-фактический-расход).

## 1. Что вызывает LLM сейчас и что планируется

**Сейчас в коде** (`lib/llm/*`, вызывающие — `lib/coach.ts`, `lib/bot.ts`, `/api/stt`):
- Все вызовы модели идут через одну обёртку `llmCall` (`lib/llm/client.ts`, OpenAI-совместимый Chat Completions на `fetch`). Без ключа (`LLM_API_KEY` / `OPENAI_API_KEY`) или при `LLM_ENABLED=0` вызовов нет, стоимость нулевая.
- Разбор намерения (`intent_parse`): сначала regex-парсер, LLM — только если он не уверен (ничего не распознал в сообщении со словами). Модель классифицирует и возвращает дословный текст суммы, сумму проверяет детерминированный код. Квоту AI-ответов разбор не тратит.
- Голос (`voice_transcribe`): `/audio/transcriptions` (`STT_MODEL=whisper-1`), стоимость посекундно.
- Ответ с цифрами всегда строится шаблоном из результата движка. Объяснения, сравнения, разговор о цели и недельный разбор (`explain`, `compare`, `goal_chat`, `weekly_review`) уже есть в перечне назначений и бюджете, но в продукте пока не вызываются.
- Онбординг идёт по `RulePolicy` (правила). `LlmPolicy` описана как интерфейс-заглушка и не подключена.

**Прокси акселератора** ([ARCHITECTURE.md](ARCHITECTURE.md#7-llm-слой)): OpenAI-совместимый прокси `https://shared1.multitool.works:4000/v1` с цепочкой моделей `gigachat3.5-432b-a28b → qwen3.5-397b-a17b → deepseek-v4-pro`. Движок считает числа, LLM разбирает запрос и объясняет готовый результат. Цепочка задана по умолчанию в `lib/llm/config.ts`, переход на следующую модель — при 5xx, 429, сетевой ошибке и таймауте попытки. Расчёт ниже сделан для этой схемы; ключ `accelerator-*` пока не получен.

## 3. Модель использования (Core Product Loop)

Core Product Loop: пользователь проходит знакомство один раз → каждый день видит, сколько можно потратить сегодня → перед покупкой спрашивает «Можно?» → получает расчёт и объяснение → записывает трату или доход → получает мягкое напоминание (платёж, доход, незавершённое знакомство) и возвращается.

Предположения о токенах на один вызов (системный промпт, JSON-схема, Evidence от движка, короткая история):

| Вызов | Когда | Вход, токенов | Выход, токенов |
|---|---|---|---|
| Разбор намерения | каждое сообщение пользователя («Можно?», запись траты, уточнение) | 700 | 60 |
| Объяснение результата «Можно?» | на каждый вопрос с расчётом | 1 300 | 180 |
| Ежедневная проверка бюджета | утренний «сколько можно сегодня» | 1 000 | 120 |
| Уточнение в диалоге | вопрос с историей разговора | 2 500 | 220 |
| Персональное напоминание | не больше 1 в день (`DAILY_CAP`) | 800 | 90 |
| Ход онбординга | извлечение ответа + выбор вопроса, ~9 ходов, один раз на пользователя | 1 100 | 110 |

Сценарии на 1 DAU в день:

| Параметр | Эконом | База | Активный |
|---|---|---|---|
| Проверка бюджета | 1 | 1 | 2 |
| Вопросов «Можно?» | 1 | 3 | 8 |
| Записей трат/доходов | 1 | 2 | 5 |
| Уточнений в диалоге | 0 | 1 | 3 |
| Напоминаний с LLM | 0 | 0,5 | 1 |
| Доля новых пользователей среди DAU (онбординг) | 10% | 15% | 20% |
| Повторы и fallback на следующую модель | +3% | +5% | +10% |
| **Итого LLM-вызовов на DAU** | **5,1** | **13,5** | **35,0** |
| **Токенов на DAU: вход / выход** | **4 831 / 535** | **14 159 / 1 505** | **37 268 / 3 947** |

Формула: `₽/DAU/день = Σ (вызовов × токенов_вход × цена_вход + вызовов × токенов_выход × цена_выход) / 10^6 × (1 + доля повторов)`.

## 5. Сравнение с бюджетом команды

| Бюджет | База, GigaChat 3.5 Ultra (53 905 ₽ на 1000 DAU в месяц) | База, оптимизированный (38 603 ₽) | Эконом, GigaChat (18 573 ₽) | База, цепочка 90/7/3 (82 477 ₽) |
|---|---|---|---|---|
| 50 000 ₽ | 0,9 месяца при 1000 DAU | 1,3 месяца | 2,7 месяца | 0,6 месяца |
| 75 000 ₽ | 1,4 месяца | 1,9 месяца | 4,0 месяца | 0,9 месяца |

Выводы:
- При основной модели GigaChat 3.5 Ultra базовый сценарий стоит около 1,8 ₽ на DAU в день и 54 ₽ на DAU в месяц. 1000 DAU весь месяц укладываются в 75 000 ₽, но не в 50 000 ₽.
- С гибридным разбором (regex + малая модель) базовый сценарий укладывается в 50 000 ₽ при 1000 DAU в месяц: 38 603 ₽.
- Qwen3.5-397B по строке 267-268 в 8-9 раз дороже GigaChat 3.5 Ultra. Как постоянная основная модель он не подходит, его стоит держать только резервом. Доля резервных вызовов прямо влияет на бюджет: каждые 10% трафика на Qwen (267-268) добавляют около 1,3 ₽ на DAU в день в базовом сценарии.
- По плану программы аудитория растёт до 1000 DAU постепенно, поэтому фактический расход за программу будет ниже, чем при 1000 DAU с первого дня. Отдельно нужно заложить расход на разработку и тесты промптов: [НУЖНО УТОЧНИТЬ].

## 6. Как снизить и контролировать стоимость

1. Regex первым, LLM только при неуверенном разборе — **сделано** (`regexUnsure` в `lib/coach.ts`).
2. Классификация намерения малой моделью, большая модель только для объяснений — **готово к включению**: `LLM_MODEL_INTENT=<id малой модели>` (например, GigaChat3-10B, если она есть у прокси); цепочка тогда «малая → основная → резервные».
3. Шаблонные ответы для простых вердиктов (`fits_plan`) без вызова LLM; объяснение по запросу «почему?».
4. Короткий системный промпт и Evidence в компактном JSON. Объяснение не длиннее 120-180 токенов. Потолки выходных токенов по назначению — `DEFAULT_MAX_TOKENS` в `lib/llm/config.ts`, общий — `LLM_MAX_OUTPUT_TOKENS`, длина входа — `LLM_MAX_INPUT_CHARS`.
5. Ночной тариф для недельных разборов (DeepSeek-V4-Pro 122 / 292,8 ₽, Qwen3.5-397B 48,8 / 317,2 ₽ за 1 млн).
6. Лимиты запросов: `chat` 30 в минуту и 500 в сутки на пользователя (`lib/rate-limit.ts`). Бюджет LLM — **сделано**: атомарный дневной потолок проекта `LLM_DAILY_BUDGET_RUB` (по умолчанию 2 850 ₽), мягкий лимит пользователя `LLM_USER_DAILY_SOFT_CAP_RUB` (3 ₽) и весь бюджет акселератора `LLM_TOTAL_BUDGET_RUB` (50 000 ₽; расширенный `LLM_TOTAL_BUDGET_MAX_RUB` = 75 000 ₽ только показывается). Дни — по Москве. При отказе ответ уходит шаблоном с теми же числами движка.
7. Журнал вызовов — **сделано**: `ai_usage` (см. §7).

## 7. Как измеряется фактический расход

Каждая попытка вызова пишется в `ai_usage` (миграция 009): назначение (`intent_parse`, `explain`, `compare`, `goal_chat`, `weekly_review`, `voice_transcribe`, `onboarding`), провайдер, модель, `prompt_tokens` / `completion_tokens` из поля `usage` ответа (если провайдер его не вернул — оценка по длине текста, `usage_estimated = true`), секунды аудио, стоимость `cost_microrub` (целые микрорубли; `cost_kopecks` — производная колонка с дробными копейками), резерв, версия цены, задержка, итог (`ok`, `fallback`, `error`, `timeout`, `budget_denied`), код ошибки и модель, с которой ушли на резерв. Попытки одной операции связаны `request_id`.

Правила списания: успешный ответ — по факту `usage`; невалидный ответ — тоже по факту (токены потрачены); таймаут — консервативно по оценке входа (провайдер мог начать считать); 5xx, 429 и сетевые ошибки — 0; отказ бюджета — 0, вызова не было.

Бюджет — таблица `budget_buckets`: перед попыткой одна условная вставка/обновление резервирует максимальную стоимость (оценка входа по длине, ~2 символа на токен, плюс `max_tokens` по цене этой модели) сразу у трёх счётчиков: весь бюджет, день проекта, день пользователя. Если хотя бы один не вмещает резерв, транзакция откатывается. Postgres блокирует строку счётчика, поэтому параллельные запросы не пробивают потолок (тест `tests/llm.test.ts` на PGlite и `tests/llm-pg.test.ts` на настоящем Postgres с пулом 24 соединения). После ответа резерв снимается, добавляется факт. Факт может превысить резерв, только если провайдер насчитал больше входных токенов, чем дала оценка; перерасход ограничен одним вызовом.

Где смотреть: дашборд `/internal/analytics`, раздел 8 «Модели и расходы»; выгрузка `scripts/export-metrics.ts` → `llm_daily.csv` (и `ai_usage_log.csv` с `--raw`).

Стоимость на DAU за день (Postgres; команда, тесты и демо исключены):

```sql
WITH cost AS (
  SELECT budget_day AS day, sum(cost_microrub) / 1e6 AS rub
    FROM ai_usage WHERE NOT internal AND NOT demo AND budget_day >= current_date - 30
   GROUP BY 1),
dau AS (
  SELECT (occurred_at AT TIME ZONE 'Europe/Moscow')::date AS day, count(DISTINCT subject) AS dau
    FROM analytics_events_real WHERE name = 'user_active' AND NOT demo AND occurred_at >= current_date - 31
   GROUP BY 1)
SELECT c.day, round(c.rub::numeric, 2) AS rub, d.dau, round((c.rub / NULLIF(d.dau, 0))::numeric, 3) AS rub_per_dau
  FROM cost c LEFT JOIN dau d USING (day) ORDER BY 1;
```

Расход по моделям и доля резервных ответов:

```sql
SELECT model, count(*) FILTER (WHERE status IN ('ok', 'fallback')) AS answers,
       count(*) FILTER (WHERE status = 'fallback') AS fallback_answers,
       round(sum(cost_microrub) / 1e6, 2) AS rub
  FROM ai_usage WHERE NOT demo AND budget_day >= current_date - 7 GROUP BY 1 ORDER BY rub DESC;
```

Сравнивайте `rub_per_dau` с оценками §4–5: база оптимизированная — 1,29 ₽, база — 1,80 ₽ на DAU в день. Дашборд считает DAU за UTC-день, как остальные метрики, а SQL выше — за день по Москве; расхождение небольшое.
